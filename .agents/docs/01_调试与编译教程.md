# OxideTerm Windows 调试与编译全流程教程

本文档专为 Windows 平台开发者（特别是刚接触 Rust 客户端开发的小白）编写，提供从**日常代码调试**到**正式发布打包**的完整操作指引。

---

## 1. 项目基础概念速览

OxideTerm 是一个基于 Rust 语言与 GPUI 高性能 GPU 渲染框架构建的现代跨平台终端客户端。主要输出目标包含两部分：
- **桌面客户端（主程序）**：对应包名为 `oxideterm-gpui-app`（生成 `oxideterm.exe` 或 `oxideterm-native.exe`）
- **命令行工具**：对应包名为 `oxideterm-cli`（生成伴生 CLI 工具 `oxideterm.exe`）

---

## 2. 日常开发：运行与快速验证

在编写代码时，你无需每次都构建完整的正式安装包。Rust 提供了快速验证和开发模式。

### 2.1 快速语法与类型检查（最快，不生成文件）
在修改了 Rust 代码后，先运行检查，几秒内即可知道是否有语法或类型错误：
```powershell
# 仅检查主程序及其依赖
cargo check -p oxideterm-gpui-app

# 检查 CLI 命令行工具
cargo check -p oxideterm-cli
```

### 2.2 直接运行开发版（Debug 模式，最推荐）
Debug 模式包含完整的调试符号且开启增量编译，适合边改边看实际效果：
```powershell
# 启动 OxideTerm 桌面客户端（32G/48G 内存推荐 -j 10 或 -j 12，初次编译大幅提速）
cargo run -p oxideterm-gpui-app -j 10

# 运行 OxideTerm 命令行工具的健康诊断指令
cargo run -p oxideterm-cli -- doctor
```

### 2.3 修改功能后，如何最快看到效果？（实战工作流）

| 你修改的内容 | 最佳查看方式 | 核心命令 / 操作 | 优势与耗时 |
| :--- | :--- | :--- | :--- |
| **界面样式 / 窗口布局 / 交互点击** | **直接启动窗口** | `cargo run -p oxideterm-gpui-app -j 4` | **增量编译仅需 3~10 秒**，编译完成自动拉起窗口体验实际效果。按 `Ctrl + C` 或关闭窗口退出。 |
| **需要看局部变量 / 抓取复杂 Bug** | **IDE 一键断点调试** | 按键盘 **`F5`**（使用预置配置） | 自动编译、自动挂载调试器并启动，断点处自动暂停，方便查看变量与调用栈。 |
| **纯后端逻辑 / 数据解析 / 算法** | **单测验证（最快）** | `cargo test -p <对应模块名> <测试用例名>` | **仅需 1~2 秒**，无需启动重量级 GPU 窗口，直接用代码验证输入输出。 |
| **刚敲完大段代码，先防手抖** | **快速语法/类型检查** | `cargo check -p oxideterm-gpui-app` | **只需 2~3 秒**，不生成 exe 文件，最快速度发现漏分号、类型不匹配。 |

> **提示**：日常修改界面时，在终端直接按键盘 **`↑`（上箭头）** 调出上一条 `cargo run -p oxideterm-gpui-app -j 4` 回车，几秒钟就能看到最新改动。

## 3. 图形化断点调试（VS Code / IDE）

项目中已预置了 `.vscode/launch.json` 和 `.vscode/tasks.json`，支持一键断点调试。

### 3.1 调试步骤
1. **打开调试面板**：点击 IDE 左侧活动栏的 **“运行与调试 (Run and Debug)”** 图标，或按快捷键 `Ctrl + Shift + D`。
2. **选择调试配置**：在顶部下拉框中选择 **`Debug OxideTerm (MSVC C++)`**（针对 Windows MSVC 工具链首选）。
3. **设置断点**：打开任何你想调试的 `.rs` 源码文件（例如 `crates/oxideterm-gpui-app/src/main.rs`），点击行号左侧区域打上红点断点。
4. **启动调试**：按键盘 **`F5`**。
   - IDE 会自动调用 `cargo build` 编译出带调试符号的程序；
   - 自动挂载调试器并启动窗口；
   - 程序执行到断点处时会自动暂停，你可以在左侧查看**局部变量 (Variables)**、**调用栈 (Call Stack)**，并使用顶部工具栏进行**单步跳过 (F10)**、**单步步入 (F11)**。

## 4. 编译正式 Release 生产包与性能对比

### 4.1 手动编译命令
在准备提交正式版本、进行性能测试或分享给他人使用时，需要构建经过全速优化的 Release 版本（建议带 `-j 4` 控制并发编译内存）：

```powershell
# 编译 Release 版桌面客户端（产物位于 target\release\oxideterm-native.exe）
cargo build --release -p oxideterm-gpui-app -j 4

# 编译 Release 版 CLI 命令行工具（产物位于 target\release\oxideterm.exe）
cargo build --release -p oxideterm-cli -j 4
```

### 4.2 Debug（开发模式）与 Release（正式模式）核心区别

| 维度 | `cargo build -p oxideterm-gpui-app -j 4` (Debug) | `cargo build --release -p oxideterm-gpui-app` (Release) |
| :--- | :--- | :--- |
| **编译模式 (Profile)** | **Debug / Dev（开发模式）** | **Release（正式生产模式）** |
| **耗时对比** | **较快**（初次编译几分钟，后续增量仅 3~10 秒） | **极长**（通常是开发版的 3~10 倍以上） |
| **优化级别 (`opt-level`)** | `0`（几乎不做耗时优化，快速出机器码） | `3`（LLVM 最高级别优化与全工程内联） |
| **链接时优化 (LTO)** | 关闭 | **开启 `lto = "thin"`**（跨 90+ 模块深度链接，链接阶段耗时极长） |
| **并行生成单元 (`codegen-units`)** | 默认多核并发生成 | **强制为 `1`**（无法多核并行生成机器码，极大拉长耗时以换取极致体积） |
| **增量编译 (`incremental`)** | 开启（改哪里编哪里） | 关闭（每次尽量全局深度优化） |
| **产物位置与体积** | `target\debug\`（几百 MB，含完整调试符号） | `target\release\`（数十 MB，已自动 strip 剥离符号） |
| **适用场景** | **日常写代码、看效果、断点调试** | **正式发布、性能压测、交付他人使用** |

## 5. 常见问题与避坑指南

### 5.1 内存不足 / 编译时闪退报错（exit code: 0xc000012d）
- **现象**：提示 `memory allocation failed` 或 `exit code: 0xc000012d`。
- **原因**：本项目包含 90+ 个 crate 模块和大量 C/C++ 语法解析器。在 16 核等高规格 CPU 上，Cargo 默认会同时启动 16 个编译器实例，瞬间占用大量系统提交内存。
- **解决办法**：加 `-j` 参数按机器内存合理设置并发线程数：
  - **16 GB 内存**：建议 `-j 4`，防止瞬时提交内存打满。
  - **32 GB ~ 48 GB 内存（当前机器配置）**：建议 **`-j 10`** 或 **`-j 12`**，既能吃满 CPU 性能，又留有充足内存余量，编译速度相比 `-j 4` 可提升 2 倍以上：
  ```powershell
  cargo run -p oxideterm-gpui-app -j 10
  ```

### 5.2 链接卡顿优化（已启用 lld-link 多核并行链接器）
- **现象**：进度停留在最后一步 `Building [====> ] 1110/1111: oxideterm-native(bin)` 较长时间。
- **原因**：Windows 默认的 MSVC `link.exe` 为单核单线程处理数百兆 PDB 调试符号。
- **已配置解决**：已在 `~/.cargo/config.toml` 中配置 `linker = "lld-link"`，调用 LLVM 多线程链接器，链接时间从原本的 1~2 分钟大幅缩短至数秒。

### 5.3 报错 `only metadata stub found for 'rlib' dependency 'core'` / 大量基础 trait 找不到
- **现象**：提示 `only metadata stub found for 'rlib' dependency 'core' please provide path to the corresponding .rmeta file`，并连锁报错找不到 `Clone`、`Sized`、`assert_eq!`。
- **原因**：
  1. Rust 工具链采用了元数据分离（Split Metadata），`libcore-*.rlib` 仅为存根，完整元数据保存在 `.rmeta` 文件中。
  2. 切换过工具链或强行中断编译后，`target/` 目录残留的增量编译元数据与当前工具链的标准库映射冲突。
- **解决办法**：
  1. 优先清理缓存：在工程根目录运行 `cargo clean`，然后重新编译。
  2. 若 clean 后仍复现，说明本地工具链的标准库损坏，运行强制修复：
     ```powershell
     rustup toolchain install 1.97.0-x86_64-pc-windows-msvc --force
     ```

### 5.3 提示找不到 `cmake` 或 `nasm`
- **原因**：某些终端窗口打开时间早于环境变量修改时间，未加载最新 `PATH`。
- **解决办法**：关闭旧终端并新开一个终端窗口即可自动生效；或在当前终端临时执行：
  ```powershell
  $env:PATH = [Environment]::GetEnvironmentVariable("Path", "Machine") + ";" + [Environment]::GetEnvironmentVariable("Path", "User")
  ```
